# DSH-board 白板使用方法

白板是随着对话共同维护的思考空间。首要目标是结构清晰、布局美观、阅读顺畅，让人愿意继续看、容易接着想。围绕当前讨论推进内容，不把一次回答或整篇材料直接铺满画布。用户明确要求完整全景、详细推导或特定风格时按其要求调整，同时保持可读性。

## 随对话生长

- 先读已有白板，辨认正在讨论的问题、已有结论、未定项与阅读路径。优先补充、修订和复用已有内容；有用的内容与用户调整过的位置应保留，避免每次回复另建一套。
- 本轮展开到足以帮助用户理解当前问题即可。宽泛主题先建立有意义的入口和主干，尚未讨论的分支留待后续追问；不要因为能想到更多方面就全部建出来，也不要自动填充所有层级和栏目。
- 不设每轮卡片数量或字数配额。依据表达需要与当前画布的承载能力决定拆分、合并和展开程度；完整性需要更多内容时，组织好主次与分区，不把所有细节平铺成同等重要的卡片。
- 生长包括修订与整合，不只是不断增加。只有新内容具有独立意义、值得回看，才新增卡片；不要把每句话、每个例子和每次回复都转成卡片。合并或改写时保留关键条件、分歧、来源与有用的用户内容。

## 先组织阅读，再放置内容

- 每轮完成后的画面应有明确入口、主次层级与阅读顺序。依据语义选择自然的从左到右或从上到下的主路径；同层内容对齐，相关内容靠近，不同主题间留白，避免远离主体的孤岛和横跨整板的无意义长线。
- 新内容先找所属位置并预留空间。卡片完整可见外框包含核心、备注和外形；备注默认可见，把正文移入备注不会消除画面拥挤。不要只按核心尺寸或存档的 w/h 猜测占地，长标题、公式和展开备注都可能扩大外框。
- 卡片之间不应重叠或遮挡。普通并列集合的边界应分离，不能让无关卡片穿入另一集合；不要用套框补救混乱的空间分布。确需共享成员时，先考虑能否用关联表达，避免多个集合框交叠得难以辨认。
- 连线应帮助读者追踪关系，保留清楚的出入口和可读标签。减少不必要的跨区连接、交叉与折返；同一区域内的关系尽量就近表达。自动绕线不能弥补错误的卡片分布，也不保证所有线互不交叉。
- 保持读者能舒适阅读的文字大小与局部密度，不通过缩小卡片或把整板缩成缩略图来容纳全部内容。全板不必一屏装下；新增区域应接得上原有结构，浏览时能辨认当前位置与上下文。
- 普通编辑负责新内容的合理放置，以及为其腾出空间所需的局部移动、对齐和间距调整；长备注或核心修改后也要考虑占地变化。保留无关区域的稳定位置。全板重排交给用户主动发起的“AI 布局整理”，不要每次回复都打乱整板。

## 核心表达与备注

- 一张卡片围绕一个核心概念、判断、问题或公式。核心应能独立表达意思，长度服从理解需要；不要只留下空泛标题，也不要把小文章或完整回答塞进卡片。
- `markdown` 是核心表达；`caption` 是独立备注，放必要解释、依据、符号与单位、适用条件、例外、来源。核心能单独读懂，备注补足理解；两处不要重复。
- 核心保留关键结论、判断或条件，让结构视图也能读懂。用普通文本即可，不必每张标题都加粗。数学表达使用 `$...$`／`$$...$$`，反引号只用于代码。
- 核心与备注都要提炼。备注保留理解所需的解释与依据，不作为长回答的收容区；较多细节可留在对话，白板保留可回看的结论与必要来源。不要为追求短而拆出大量碎片卡，或用装饰性标题卡重复集合名称。
- 不为短而删掉改变结论的条件；细节需要保留时放备注。不要为了排版把文字或公式转成图片。

## 选择合适的结构

- **父子卡**：明确的主题—子主题、概念—分项等层级，用 `parentChild` 边从父卡指向子卡。已有子卡换父用 `reparent`；保持单父、无环。先后步骤或因果关系不自动等于父子关系。
- **集合**：当边界和短名称能帮助辨认一组并列观点、方案或材料时，用 `collection` 显式归组，成员用真实卡片 ID。空间靠近已足够清楚时不必再套框。集合不是树的父节点；成员可共享，但共享应有语义必要性且不妨碍阅读。集合外框随成员实际占地派生，设置集合 x/y 不会自动排开成员或隔离其他集合。
- **关联线**：用 `association` 表达支持、依赖、对比、例证或矛盾，方向和短说明要有意义。只连接确实存在的关系，不把所有卡片都串起来，不凭空补出逻辑。必要时在备注交代关系的条件。
- **公式卡**：仍是 `type:"text"`，把核心 `markdown` 整体写成 `$...$` 或 `$$...$$`，应用会自动呈现为公式卡；不是新建一种 `formula` 类型。符号、单位和适用条件放 `caption`。混合解释性正文的卡片不会成为纯公式卡。
- 按当前问题选择结构：概念分解用层级，并列比较用分区或集合，推导与流程用有意义的关联。结构应减少理解成本；不要求同时使用全部工具，也不为显得完整而重复建立集合、标题卡和连线。

## 草稿中的流程表达

白板帮助人阅读、理解与做决定。概念、证据、推理与行动建议可以混合，待确认的条件与选项要保留。流程外观不代表可执行的 SOP。

- 文本／公式卡可选 `shape: rectangle`（步骤）、`diamond`（判断／选择）、`pill`（起止）；缺省／`card` 为普通知识卡。保留有用的核心和备注，不为外形复制卡片或删掉依据。
- 流程关联仍用 `association`，设 `directed:true,routing:"orthogonal",stroke:"solid"`，把条件或关系写在 label。父子边继续表达层级。曲线、折线、实线、虚线可混合，虚线用于补充联系时用标签说明，不靠样式断言结论。
- 需要强调阅读方向时可用 `stroke:"flowing-dashed"`，虚线沿箭头移动；无向边保持静态。少量使用，不将流动当成执行中或完成进度；PNG 仍是静态虚线。
- 既有卡片外形用 `setNodeShape`；既有边画法用 `setEdgeStyle`，after 同时提供 routing 与 stroke。null 恢复默认；不改变端点、方向、标签和内容。
- 表达多个选项时写明各自条件；人的权衡保留理由与未定项。布局任务只能移动已有卡片，不能借整理改外形、连线或替人做决定。

## 随讨论展开的例子

用户问“合力怎样影响运动”时，可围绕“合力决定加速度”组织当前解释；需要公式时保留 `$$F=ma$$`，备注说明符号、单位与适用条件。不必同时铺开整个力学知识体系。

随后用户追问“速度为零时合力一定为零吗”，先检查已有表达，在相关位置补充这个辨析及必要联系。只有讨论确实进入多个解释路径的比较时，再组织比较区域；避免把一轮回复的全部背景、例子和潜在追问提前变成分区。

## 写入与完成检查

先用 `draft_board_read` 阅读当前板，复用真实身份；内容和结构修改用 `draft_board_apply` 的一个可撤销批次。创建文本卡时可同时给出 `markdown` 与 `caption`；已有卡片的核心与备注分别用 `updateNodeText` 和 `updateNodeCaption` 更新。不要只会创建普通文本卡，也不要绕过模型直接改草稿文件。

提交前检查：本轮是否围绕当前问题、复用了已有内容？从哪里开始读，主次和顺序是否清楚？新增内容及其备注是否有足够空间？卡片或集合是否互相遮挡，连线和标签是否难以追踪？是否需要合并重复内容或减少无用框线？是否保留了关键条件、分歧与依据？

普通编辑在落盘前自动渲染只读候选，按全文展开的备注、实际卡片外框、集合预留边界、连线路径和标签检查。遇到 `E_EDIT_GEOMETRY` 时，原板、版本与历史保持不变；根据返回的 `geometry`、集合边界与具体冲突修正完整批次，仍使用原 baseContentVersion。优先调整本轮内容的局部位置与分区，不能为通过检查删掉必要关系或关键内容；需要简化结构时先确保语义保留。发生版本冲突先重读，测量不可用时请用户打开或重新载入共同白板，不绕过校验直接写文件。

普通读取中的 `layout` 若为 measured，可参考该版本已测量的几何；unmeasured 表示没有当前版本测量，不可把存档 w/h 当成实际占地。通过几何检查只说明程序约束通过，不保证语义层级、视觉主次或审美；仍需自行组织好阅读路径，不能声称已看过未提供的截图。

仅整理布局的任务遵循专用规则，只移动允许范围内的已有卡片，不能借本方法增删实体或改内容、外形、关系、集合；不调用普通编辑工具补做内容。本方法不扩大任务权限。
